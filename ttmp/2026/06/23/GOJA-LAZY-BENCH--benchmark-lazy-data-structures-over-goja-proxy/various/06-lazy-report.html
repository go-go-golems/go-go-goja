Benchmark Report · goja Lazy Data Structures

The price of laziness.

A measured study of the go-go-goja lazy module, which exposes lazily-materialised Go data to JavaScript through an ES6 Proxy. The motivating question: the module's flag-only GetOwnPropertyDescriptor is designed to make Object.keys() enumeration free of provider work. How free is it, really — and what does the laziness cost in absolute terms?

Abstract

5×5 samples

The lazy module puts a Go value behind a Proxy so that JavaScript reads a property only at the moment it is read. Its central design choice is a flag-only GetOwnPropertyDescriptor trap: it reports a key as enumerable without building the value, so that Object.keys() and for...in can list keys without ever calling the Go provider. We benchmark this against an eager object and against a naive value-materialising descriptor, over reads, enumeration, scaling, and serialisation.

First, the design goal is met and measurable. Enumerating a 100-key lazy map calls the provider 0 times; the same enumeration through a naive descriptor calls it 100 times. That count is a deterministic code-path invariant — identical across every sample — and it is the load-bearing signal of this report, the direct analogue of allocs/op in the binding-mechanism study.

Second, "free of provider work" is not "free." Lazy enumeration costs 596866 ns for 100 keys — about 15.8× an eager object's 37874 ns, because the Proxy constructs a descriptor object for every key. The flag-only descriptor eliminates the expensive work (the provider, which may scan Wi-Fi or query a database); it does not eliminate the machinery work. Lazy enumeration is for correctness — listing keys without paying for values — not for speed.

The answer to the motivating question

The flag-only descriptor succeeds at what it was designed to do: Object.keys() and for...in enumerate a lazy map with zero provider calls, versus 100 for a naive descriptor. The price of that laziness is roughly 15.8× the wall-clock cost of enumerating an eager object, paid in per-key descriptor construction. For any provider that does real work (I/O, parsing, a scan), avoiding 100 of those calls dwarfs the descriptor machinery. Reserve eager snapshots for tight loops that enumerate millions of times; keep the lazy Proxy everywhere the point is to not pay for unread values.

Method

what is measured

Every benchmark exposes a Go value to a fresh goja runtime, compiles a one-expression JavaScript program once, then runs it repeatedly. Compilation and runtime construction sit outside the timed loop, so the only thing measured is the act of touching the lazy object. Five samples at one second each (-count=5 -benchtime=1s); means and spreads are reported.

The load-bearing signal is provider/op. Each benchmark reports a custom metric: the number of times the Go provider was called per operation. It is a deterministic invariant — identical across all five samples, because it is a property of the code path, not a measurement. Nanoseconds wobble; provider/op does not. Where a configuration claims to be lazy, provider/op = 0 is the proof. Where it materialises, provider/op equals the key count.

The provider itself does trivial work (returns a pre-built string) so that the measurement isolates trap and dispatch overhead, not string formatting. This is the conservative choice: a real provider doing I/O would widen every gap in the lazy direction, because the provider calls the naive path performs would each be far more expensive than the few hundred nanoseconds measured here.

The boundary, in one picture

A JavaScript enumeration of a lazy Proxy is a two-trap cascade. Object.keys calls ownKeys once, then [[GetOwnProperty]] for every key to test enumerability. The flag-only descriptor makes that second call cheap in provider terms but not in machinery terms.

JS: Object.keys(device)       |       ▼ [[OwnPropertyKeys]]    OwnKeys(target) → ["k000", "k001", ...] (1 array)       |       ▼ for EACH key: [[GetOwnProperty]]    GetOwnPropertyDescriptor(key)                             flag-only → {enumerable:true, configurable:true} (no value, no provider)                             naive → {value: provider(key), ...} (provider called per key)

The expense lives in that per-key loop. The flag-only descriptor keeps the loop free of provider work; the naive descriptor performs the provider call inside it.

02 /

Reads — cached is cheap, cold pays the provider

obj.k000 → "val-000"

A single property read is the cheapest operation, and the cached read is the realistic hot path. Once a key has been read once, its goja.Value is memoised; every subsequent read returns the cached value with no provider call and no ToValue. A cached lazy read costs 582 ns — about 3.7× the 159 ns of reading an eager object, paying one extra allocation for the Proxy machinery.

The cold read — a Proxy with no cache, so every read calls the provider and re-converts — costs 1161 ns with 4 allocations and 1 provider/op. This is the cost a lazy read pays the first time, and what a non-caching lazy object pays every time. The module caches by default, so the cold cost is paid once per key per runtime; the steady state is the cached bar.

Cache the value, not the raw Go object. The lazy module memoises the converted goja.Value, which serves two purposes: it avoids re-running ToValue (an allocation), and it preserves identity so device.k === device.k holds. A cache keyed on the raw Go value would pay the conversion on every read.

Enumeration — the flag-only win, measured

Object.keys(device)

This is the regime the flag-only descriptor was built for. Enumerating a 100-key lazy map through the module's descriptor calls the provider 0 times. The same enumeration through a naive value-materialising descriptor calls it 100 times — once per key. The naive descriptor is only modestly slower in nanoseconds, because the provider here does trivial work; with a real provider, those 100 calls would dominate.

Mechanismns / Object.keysallocsprovider/op
Eager object (plain JS object)378741150
Lazy map (flag-only) (the module)59686610330
Naive lazy (materialising descriptor)6434751333100
Lazy map (for...in)73164614700

provider/op is a deterministic invariant, identical across all five samples. It is the proof of laziness; the nanoseconds corroborate it.

The nuance that matters. Lazy enumeration is not faster than eager enumeration — it is 15.8× slower, because the Proxy builds a descriptor object for every key. The flag-only descriptor wins on the dimension that matters: it does zero provider work, where the naive descriptor does N. When the provider is a Wi-Fi scan, that is the difference between listing keys instantly and scanning 100 times. When the provider is a pre-built string, the machinery cost dominates and an eager snapshot would be faster. Choose by what the provider does, not by the nanoseconds alone.
04 /

The deterministic signal

provider/op across operations

Plotting provider/op across every operation collapses the report to a single picture. Operations that read values materialise them; operations that only list keys do not. The boundary is sharp and it is exactly where the design said it would be.

This chart is the reason the report can make confident claims from five-sample runs. Even though nanosecond measurements wobble, provider/op pins each configuration to a fixed position, and the position is determined entirely by whether the operation reads values. A future goja version may change the nanoseconds; it cannot change the fact that Object.keys does not read values and JSON.stringify does.

05 /

Scaling

N = 10 / 100 / 1000

Enumeration cost grows linearly with the key count, and the provider-call count stays at zero throughout. This is the scaling behaviour the flag-only descriptor promises: the work is proportional to the number of keys, never to the cost of producing their values.

The per-key cost is stable: from 10 to 1000 keys, each key adds roughly 4 µs and 10 allocations. A 1000-key lazy map enumerates in 3986709 ns — under four milliseconds — without a single provider call. For a provider that scans or queries, that is the difference between an instant key listing and a thousand fetches.

06 /

Backend choice: Proxy vs DynamicObject

a 28× enumeration win

The lazy module ships two backends. Map uses an ES6 Proxy; DynMap uses goja's native DynamicObject (a 5-method Go interface: Get/Set/Has/Delete/Keys). The DynamicObject has no ES6 invariant checks and no target object, so it avoids the per-key descriptor machinery that made Proxy enumeration expensive.

Use DynamicObject unless you need an ES6-only trap. The Proxy remains the right choice only when you need construct, prototype interception, defineProperty interception, Symbol own properties, or per-key enumerability control. For a lazy map or record, DynMap is faster on every operation and simpler to reason about: Get returning nil delegates to the prototype automatically, with no manual fallthrough.

Serialisation is inherently materialising

JSON.stringify(device)

JSON.stringify is the operation the flag-only descriptor cannot help. By definition, serialisation reads every value, so it calls the provider once per key. The measurement uses a non-caching lazy map so the per-call cost is visible; with the module's cache, only the first stringify materialises, and subsequent ones read cached values.

Mechanismns / stringifyallocsprovider/op
Eager object417144250
Lazy map (no cache)2390591648101

The lazy stringify reads every value (101 provider/op) and costs 5.7× the eager stringify. This is not a flaw in the descriptor; it is the definition of serialisation. The guidance follows: for large lazy objects, do not JSON.stringify the whole proxy. Read specific keys, or install a toJSON trap that returns an explicit, compact shape.

08 /

Threats to validity

what the numbers do not say
  • No JIT, one goroutine. goja interprets bytecode and a runtime is not concurrency-safe. Absolute latency is illustrative; the provider/op counts and the ratios between mechanisms are what generalise.
  • Wall-clock on a shared laptop. Treat absolute figures as ±~10–20%; treat provider/op as exact.
  • Five samples. Enough to show the enumeration ordering and the deterministic provider counts; too few for tight confidence intervals on the nanoseconds.
  • Trivial provider. The provider returns a pre-built string, so the naive path's 100 provider calls look cheap. A real provider (I/O, a scan) would make the flag-only win far larger than the nanoseconds suggest — the provider-call count, not the time, is then the decision metric.
  • 100-key records. Enumeration is measured at N=100 with scaling to 1000. Pathological key counts were not explored, but the linear scaling in Figure 4 makes the behaviour predictable.

None of these threaten the central conclusion, which rests on the deterministic provider/op counts and on ratios measured under identical conditions.

Reproducibility

one command

The harness is go-go-goja/perf/goja/phase4_lazy_bench_test.go. From the go-go-goja module root:

go test ./perf/goja -run '^$' \ -bench 'LazyRead|LazyEnumeration|LazyScale|LazyMaterialize' \ -benchtime=1s -count=5 -benchmem | tee raw.txt

The pipeline that turned that output into this report is in the ticket: 03-parse-lazy-stats.py (raw → stats), 04-lazy-charts.py (SVG figures), 05-lazy-report-template.html + 06-make-lazy-report.py (fill the template). Every figure is inline SVG generated directly from the measured statistics — no charting library, no JavaScript, no network requests.

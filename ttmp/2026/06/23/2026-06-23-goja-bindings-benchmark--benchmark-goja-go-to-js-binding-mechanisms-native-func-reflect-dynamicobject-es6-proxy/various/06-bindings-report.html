Abstract

5×5 samples

JavaScript in goja never touches Go memory directly. Every property read, every function call, crosses a bridging layer that translates between goja’s internal Value representation and ordinary Go. There are roughly half a dozen such layers, and they are not equally cheap. We benchmark all of them performing identical work — returning the integer 42 — so that the only variable is the binding itself.

Two findings dominate. First, in the function-call regime, latency is allocation-bound. A native callable costs 220 ns and forces 3 allocations; an ordinary Go function wrapped by reflection costs 752 ns and forces 12. The added 9 allocations account almost entirely for the added 532 ns, at roughly 60–86 ns per allocation.

Second, a Go-backed ES6 Proxy is cheap, and for calls it is nearly free. A Proxy Get trap costs 191 ns per read — about 1.6× a plain object and exactly one extra allocation. A Proxy Apply trap, used to call through a proxy, adds no allocations at all over a raw native call (277 ns, same 3 allocs). The catch is statistical, not absolute: the Proxy paths are markedly noisier than their peers, so the headline ratios are robust while the raw nanoseconds are not.

The answer to the motivating question

A Go proxy object with manual dispatch costs, per property read, one additional allocation and about 1.5–1.6× the time of a plain object — roughly 191 ns. For function calls it is essentially free. For any workload where the Go side performs real work (I/O, parsing, database), this overhead is negligible. It only matters in tight loops of millions of trivial reads, and there the drop-in upgrade is a DynamicObject, not a plain object.

Method

what is and isn’t measured

The experiment holds everything constant except the binding. Every benchmark exposes a Go value to a fresh goja runtime, compiles a one-expression JavaScript program once, then runs that program repeatedly. The program always does the same logical work — evaluate add(40, 2) or read obj.v — and always yields 42, which the harness checks. Because compilation and runtime construction sit outside the timed loop, the only thing being measured is the act of crossing the Go→JS boundary.

Each configuration is sampled five times (-count=5) at one second of iterations each (-benchtime=1s), and the figures below report the mean of those samples with their spread. This sample size is small; we therefore lean on two deliberate crutches, both of which are central to how the results should be read.

The first crutch is the most important idea in this report. Go’s benchmark allocator counts allocations per operation, and that count is deterministic — an invariant of the code path, not a measurement. Across all five samples, for every configuration, the allocation count is identical to the single allocation. (That is why benchstat prints “±∞” on those columns: the variance is zero, and with fewer than six samples it declines to draw a confidence interval.) Nanoseconds vary run to run; allocation counts do not. Treat the allocation count as the load-bearing signal and the nanoseconds as corroboration.

The second crutch is honesty about the nanosecond. The measurements were taken on a shared laptop running an interpreted, single-goroutine runtime with no JIT. Absolute latency is therefore illustrative; the ratios between mechanisms, and especially the allocation counts, are what generalize. We quantify the noise explicitly in §5, where it becomes a finding in its own right.

The boundary, in one picture

To read the numbers, one must picture the boundary they describe. A JavaScript expression such as svc.Add(40, 2) is compiled to bytecode and executed by goja’s interpreter (vm.go). When the VM needs a property of svc or wants to call it, it does not reach into Go. It asks an object — an implementation of goja’s internal objectImpl interface — to do the work on Go’s behalf. Different binding mechanisms are simply different objectImpl implementations, each with its own dispatch path and its own allocation signature.

JS bytecode    svc.Add(40, 2)       |        (vm.go: stack machine, no JIT)       ▼ objectImpl    getStr("Add") → assertCallable → vmCall(call)       |       one implementation per binding mechanism:       ▼       nativeFunc   → func(FunctionCall) Value (no reflection)                   objectGoReflect → reflect.Value + reflect.Call (the 12-alloc path)                   dynamicObject → your Get/Set/Has/... (Go interface)                   proxyObject → ES6 traps + invariant checks       ▼ your Go code

The expense lives entirely in the middle layer. The question this report answers is how thick that layer is, one implementation at a time.

Function calls — an allocation-bound regime

add(40, 2) → 42

A JavaScript function call into Go has two possible shapes, decided the instant you pass the value to vm.Set. If the Go value has the exact signature func(goja.FunctionCall) goja.Value, goja recognizes it as a native callable and stores it verbatim — the VM’s call trampoline (func.go:558) invokes it with no translation. Any other function type falls through a type switch to a reflection wrapper (runtime.go:1973) that, on every single call, reflects each argument into the parameter type, allocates a []reflect.Value, performs a reflect.Call, and re-boxes the result.

The difference between those two shapes is the entire story of this section, and it is large: a factor of 752 / 220 ≈ 3.4 in time, and 12 / 3 = 4× in allocations. Observe that the allocation ratio is the clean number, because it is an invariant.

Reading the four calls in the middle

Between the two extremes sit four mechanisms, and their allocation counts explain their order almost completely:

Mechanismns/callallocsmarginal ns/alloc
Wrapped func (reflect.Call, 2 args)7521259
Map of funcs (func re-wrapped every access)17372184
Reflect struct method (method lookup + reflect.Call)20172486

Marginal cost is computed against the native floor (3 allocs, 220 ns): Δns / Δallocs. It rises from 59 to ~85 ns/alloc as the path accumulates reflection machinery on top of each allocation.

The marginal cost of one allocation is not constant: it climbs from 59 ns for a plain wrapped function to roughly 85 ns once the path also performs a reflective method lookup or re-wraps a function on every access. This is the deep structure behind the headline number — an allocation costs a baseline amount, and the reflection work that surrounds the allocation adds more. The reflect-struct-method path at 2017 ns is the slowest not because it allocates the most bytes (it does) but because it stacks two full reflection traversals: resolve the method, then marshal its arguments.

A surprise worth flagging. Storing a Go function inside a map[string]interface{} and reading it back from JavaScript (m.add(40, 2)) costs 1737 ns — slower than a reflect-struct method would be if it did less work, and far slower than the 752 ns the same function costs when set directly. The map is a live view: each access returns the raw interface{}, and goja re-wraps it through reflection on every single call. The map is not caching the function; it is re-deriving it each time. If JavaScript calls a function stored in a live map in a loop, pay the one-time cost to hoist it into a vm.NewObject() instead.

The single relationship that explains almost everything

allocations → latency

Plotted together, all sixteen configurations reduce to one picture. Latency rises with allocation count along a near-linear trend, and the trend’s slope — about 86 ns per allocation — is the unifying constant of the call regime. This is the figure to remember.

This single chart is the reason the report can make confident claims from five-sample runs: even though individual nanosecond measurements wobble, the allocation count pins each point to a fixed horizontal position, and the latency then falls on a line whose slope is stable. A mechanism that forces more allocations will cost more, and the figure tells you by roughly how much before you measure it.

The reads’ refusal to climb the ray is itself the finding of the next section: in the read regime, the dominant cost is the fixed overhead of a property dispatch, not the allocation it may or may not trigger. One allocation or two, the read costs ~120–190 ns either way.

04 /

Property reads — a fixed-overhead regime

obj.v → 42

Reading a property is cheaper than calling a function, and the ranking of mechanisms is different. Here the floor is a cluster of one-allocation readers at roughly 123 ns: a reused plain JavaScript object, a live Go map, and a DynamicObject. They are statistically indistinguishable from one another — the DynamicObject at 124 ns is within the run-to-run noise of the plain object. A fully Go-controlled object can be as fast to read as a plain JavaScript object.

The two-allocation readers — reflect struct field, DynamicArray, and the Proxy — all pay one extra allocation over the floor and land at roughly 1.4–1.6× its cost. That is consistent with the call regime’s marginal cost: one allocation is worth about 60–86 ns, and the read delta is 123 → 191 ns, i.e. ~69 ns for one allocation. The two regimes agree, which is reassuring.

For reads, prefer DynamicObject over Proxy. Both give Go full control over what JavaScript sees. But the DynamicObject lands on the one-allocation floor at 124 ns with a five-method interface (Get/Set/Has/Delete/Keys), while the Proxy pays a second allocation at 191 ns to enforce ES6 invariants against its target. Reserve the Proxy for when you genuinely need an ES6-only trap — construct, ownKeys, set interception — that the dynamic interface cannot express.

The Proxy, dissected

machinery vs. dispatch vs. noise

The motivating question concerns the Proxy specifically, so it earns its own dissection. Three things must be separated: the cost of the Proxy machinery (the runtime’s invariant checking), the cost of the dispatch logic you write inside the trap, and the noise of measuring the Proxy at all.

The dispatch body barely matters; the noise dominates

We held the Proxy machinery fixed and varied only the body of the Get trap. A switch that hits, a map that hits, and a miss that returns undefined — the three sensible ways to write a manual-dispatch trap.

Trap bodymean nsCVallocsnote
switch — hit1583.7%2fastest & most stable
map — hit19921.7%2bimodal: 173 or 275
miss → undefined21828.8%2walks the prototype chain

CV is the coefficient of variation (stddev / mean). A switch-dispatch Proxy is an order of magnitude more predictable than a miss.

The result is counter-intuitive and worth stating plainly: a hit is faster than a miss. When the trap returns a value, the lookup terminates; when it returns undefined, goja is obligated to keep searching the proxy target’s prototype chain before conceding. So the dispatch logic you write does matter, but in the opposite direction from a naïve guess — early-return-on-hit is not just clearer, it is faster.

The noise is itself the finding. Non-Proxy measurements in this report have coefficients of variation under 5% — the native function is 1.5%, the wrapped function 0.8%. The Proxy property read is 18.2%, and the miss is 28.8%. The Proxy path is intrinsically more variable. The likely cause is its invariant-checking machinery — proxyObject.getStr re-inspects the target’s own property on every access (proxy.go:601), a data-dependent branch that interacts unpredictably with the cache and the garbage collector. Plan around the median, and do not trust any single Proxy sample.

Calling through a Proxy is essentially free

The read path is where the Proxy spends its budget; the call path is not. Fronting a callable target with a Proxy and invoking it through the Apply trap costs 277 ns with 3 allocations — byte-for-byte the same allocation signature as a raw native call, and only ~57 ns slower for the one extra Go-callback hop. If your design calls a proxy rather than reading it, the Proxy machinery is not a cost worth worrying about.

Threats to validity

what the numbers do not say

A benchmark is only as trustworthy as its stated limits. The important caveats for this one:

  • No JIT, one goroutine. goja interprets bytecode and a runtime is not concurrency-safe. These are single-threaded, interpreted numbers. A future JIT would compress absolute latency but is unlikely to reorder the mechanisms, because the reflection wrapper’s allocations would remain.
  • Wall-clock on a shared machine. The nanoseconds were taken on an interactive laptop. Treat every absolute figure as ±~10–20%; treat every ratio and every allocation count as robust.
  • Five samples. Enough to expose the Proxy’s instability (its CV is large), too few for tight confidence intervals. The deterministic allocation counts compensate, which is why they are foregrounded throughout.
  • Single-key reads only. Each read fetches one property. We did not measure enumeration — Object.keys, for…in, JSON.stringify — which for a Proxy is a multi-trap cascade and likely the regime where its overhead is largest. This is the obvious next experiment.
  • One payload. Every call returns a small integer. Larger or nested return values would add conversion cost that is orthogonal to the binding choice and is not captured here.

None of these threaten the central conclusions, because the conclusions rest on allocation counts and on ratios between mechanisms measured under identical conditions, both of which are insulated from the caveats above.

Reproducibility

one command

The harness is go-go-goja/perf/goja/phase3_bindings_bench_test.go. From the go-go-goja module root:

go test ./perf/goja -run '^$' \ -bench 'BindingFunctionCall|BindingPropertyGet|BindingArrayIndexGet|ProxyDispatchDetail' \ -benchtime=1s -count=5 -benchmem | tee raw.txt benchstat raw.txt

Or, using the ticket’s bundled reproducer, bash scripts/02-run-bindings-bench.sh /tmp/out. The raw five-sample output and the benchstat aggregation from which every figure here was derived are filed alongside this report in the ticket.
